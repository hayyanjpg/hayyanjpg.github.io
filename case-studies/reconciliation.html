RECONCILIATION PIPELINE

Order vs payment dari dua channel, 16 aturan audit SQL, dan bukti bahwa aturannya nggak cuma jalan — tapi juga nggak bikin false positive.

ROLE: DATA / AI ENGINEER PYTHON · SQL · FASTAPI · REACT · STREAMLIT CI HIJAU · 39 TESTS 2026

01 // MASALAH

Order masuk dari Web dan Mobile App dengan format yang berbeda. Tanpa rekonsiliasi, selisih nominal, order tanpa pembayaran, pembayaran yatim, dan duplikat baru ketemu setelah data masuk ke warehouse — saat sudah terlambat untuk dicegah.

Tantangannya bukan cuma mendeteksi anomali, tapi memastikan aturan yang dibuat nggak menuduh transaksi yang sehat.

02 // BATASAN & ASUMSI

  • Dataset sintetis, bukan data produksi.
  • SQLite dipakai supaya pipeline portabel; produksi sebaiknya PostgreSQL.
  • Belum ada scheduler dan alerting (Slack/email).
  • Dashboard dijalankan lokal, belum di-deploy publik.

Batasan ini saya sebut di depan supaya penilaian berfokus pada cara berpikir, bukan klaim yang berlebihan.

03 // ALUR & KEPUTUSAN

Ingestion CSV mentah → normalisasi skema → 16 aturan audit SQL → rekonsiliasi order vs payment → laporan harian → dashboard React/Streamlit.

Dua keputusan yang saya jaga:

  • Dua dataset, bukan satu. Dataset kotor dipakai untuk membuktikan tiap aturan bisa mendeteksi anomali. Dataset bersih dipakai untuk membuktikan aturan yang sama nggak menghasilkan false positive. Tanpa dataset bersih, deteksi 100% bisa berarti sistem cuma menuduh semuanya.
  • SQLite dulu, PostgreSQL nanti. Portabilitas lebih penting di tahap portofolio; desain tabel dan SQL check sudah disiapkan supaya bisa dipindah tanpa mengubah logika.
